# 三个 Lin 插件的源码兼容性检查

按用户要求，只检查公开源码并做隔离的代码测试，不接入用户 ST，不发送真实模型请求。

| 插件 | 审阅版本/提交 | 与动态人格的关系 |
| --- | --- | --- |
| lin-dynamic-persona | 本仓库 0.1.0 | 生成前单个 setExtensionPrompt 槽位；独立 IndexedDB；后台 generateRaw |
| lin-emotional-control | 1.2.0 / `479e942f7af61d3ecbd9bbe45294f64120d1eff5` | 最终请求前部的情绪说明；默认协作模式把即时/目标与抽签留给旧插件 |
| lin-prefill-guard | 1.3.0 / `475c555bca1831c402554b1262c762ce85911096` | 处理尾部预填充/语义承接；跳过 quiet 分析；独立设置与诊断键 |

## 结论

在以上已审阅版本和默认协作模式下，**没有发现直接的存储键、生成钩子或提示位置冲突**。这不是对所有模型输出和其他插件组合的无限保证。

- 新插件不监听/改写 `CHAT_COMPLETION_SETTINGS_READY`。其人格提示已经在 ST 组装正式 messages 之前进入系统/故事区域，因此不会插在预填充助手最终确认之后，也不破坏助手用来核对发送顺序的请求快照。
- 预填充助手 `planInjection` 对 `quiet` 提前返回；新插件后台分析走 generateRaw 的 quiet 请求，不被当作正式剧情加上尾部承接。
- 旧情绪插件需要生成事务以及已组装消息对象的引用才会作用于请求；独立 raw 分析没有这条正式剧情请求链。
- 三者的设置/元数据键分别为 `lin_dynamic_persona`、`human_temper_v1`、`lin_prefill_guard_v1`。新插件不写另两个插件的数据。
- 预填充助手的恢复按钮调用 ST 原生 `generate('continue'/'regenerate')`，不直接改写聊天。这两种操作走新插件已有分支/续写逻辑。
- 旧情绪插件与新插件都能产生即时状态，这是功能重叠而非“天然零冲突”。默认协作模式排除新插件的即时层、目标层和演出抽签；完全接管模式要求先停用旧插件。
- 旧预填充助手可能根据它自己的设置改写 max_tokens/reasoning_effort；这些是该插件原本的行为。本动态人格扩展不会额外改写、清除或抵消它们。

## 源码组合验证

导入两份参考项目的实际纯函数，检查预填充规划在不同模式、旧情绪说明先后插入两种顺序下保留人格系统块且旧情绪仅出现一次；另检查 quiet 跳过。新插件生成前提示不会占用请求尾部。测试记录详见 TEST-REPORT.md。

因用户要求停止实机 ST 联调，未把“源码和宿主模拟测试通过”表述成“已验证真实 Vertex Gemini 成功输出”。
